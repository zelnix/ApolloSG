# ApolloSG — TC Hawkeye Calibration Report

Scope: the 12 failing cases in `tests/test_calibration_reference_library.py`, resolved by fixing
shared detection/scoring logic in `triage.py`, `checks.py`, `scoring.py`, `decide.py`, `patterns.py`
and `indicators.py` — no artificial score bumps, no weakened thresholds, no case-specific branches.
Fresh baseline before this pass: **12 failed / 25 passed / 21 skipped** (not 17/18 — the previous
session's partial fixes had already closed some gaps; see `git log` for that history).
After this pass: **0 failed / 35 passed / 23 skipped** — confirmed by two full `pytest` runs and a
standalone diagnostic script that recomputed every case's score and routing before/after.

Live numbers for every settled case are in `content/calibration_results.json`, regenerated by the
suite itself on every run (`test_calibration_report_is_written`): **32/55 cases settled by TC
Hawkeye alone, 32/32 tier matches (100%)**. The other 23 correctly escalate to Magnum DI's reasoning
— PRD-intended, not a gap (see "Architecture issue" below).

## Case-by-case root cause and fix

| Case | Scenario | Root cause | Fix |
|---|---|---|---|
| 004 | OAuth consent phishing | "Approve the request…requesting full access" isn't `enter/provide/confirm…password` — no request extracted at all | New credentials-request alternative: `request(ing)/approve/authorise/grant … access to your/the …` |
| 029, 065, 080, 083 | Family/romance/remote-access/court scams, all **confirmed_scam** | A full KB-pattern match (L2) was returned by the old rule-based waterfall as `likely_scam` *before the 0–100 score was ever consulted* — even when the score's decisive-mechanism floor had already reached 85+ | **Architecture fix** (see below): `decide.py`'s `provisional()` now escalates an L-rule's `likely_scam` to `scam` when an independent decisive signal (not the circular pattern-match itself) is also present. For these four, that signal is **severe-consequence manipulation** — secrecy/isolation ("don't tell anyone"), acute distress ("I'm so scared"), or an arrest/authority threat ("a warrant has been issued", "report this to the authorities") — a new, generically useful detector, not case-specific wording |
| 071 | Fake online store | "Pay now…with your card details" has no verb (`enter/provide/…`) before "card details", so no request matched | New credentials alternative: `with your card details/number`; added `fake_online_store` KB pattern |
| 075 | Money-mule recruitment | "Reply with your account details" — "reply with" wasn't a `personal_details` verb, and bare "account details" (no "bank" prefix) wasn't a keyword | Added `reply with` verb and `account details` keyword; added `money_mule_recruitment` KB pattern + a dedicated money-mule decisive signal |
| 085 | myGov benefits phishing | "by **entering** your myGov password" — the verb list only had the bare infinitive (`enter`, not `entering`) | Added `-ing`/`-ing or -e` inflections to the `credentials` and `personal_details` verb groups (`enter(?:ing)?`, `provid(?:e\|ing)`, …) — a general phrasing gap affecting any continuous-tense scam message |
| 101 | Legitimate Uber notification | "Uber" isn't in the recognised-brand table, so the ground-truth "official, clear" fact for it was silently never attached to any check | Added `uber` to `BRANDS` |
| 104 | Legitimate interview confirmation | No brand, no links, no requests — a genuine "nothing to check" message, but "No payment is required at any stage" is a *positive* legitimacy statement, not silence, and the floor logic treated it the same as a content-free message | New `explicit_no_request` detector (e.g. "no payment is required", "contains no links", "does not ask for any information"); when present with no consequential request and no concerning fact anywhere, the benign floor no longer applies |
| 005, 013 | "IT Support" account-recovery callback; "NAB" bank callback | The `call us back on …` request regex failed on realistic phrasing (`call us **back** on`, `call us back **urgently** on` — the filler words sit between the verb and the trigger word the old regex required adjacent); once fixed, the callback is a real, unverified consequential request from a named sender with nothing to corroborate it one way or the other | Fixed the regex; extended the "call-back is consequential" rule (already brand-gated) to also cover a generic self-identified sender ("this is IT Support"). Both cases now correctly **escalate to Magnum DI** instead of settling at a wrong score — this is the PRD's own "reasoning" capability, documented in `decide.py`, for exactly this shape: *an ask through a route nobody verified, with nothing else to settle it* |

## Architecture issue fixed (not a per-case patch)

`decide.py` carried two separate "which Finding applies" evaluators: an older rule waterfall
(S1–S4 / N1–N4 / L1–L3) used for the *first* decision it could reach, and the 0–100 Findings Rating
(`scoring.score_plan`) used only as a *last-resort fallback* when the waterfall found nothing at all.
Whenever the waterfall reached an L-rule (`likely_scam`), the score was never looked at again — even
if the score's own decisive-mechanism floor had already reached "scam". A full diagnostic sweep of
all 55 cases confirmed this was a real, general defect (not isolated to the 4 cases above): e.g. case
026 ("Hi Mum", **suspicious**, target `likely_scam`) already reached score 85 internally today, purely
because a full pattern match treats itself as its own corroboration — so a blanket "always trust the
score" fix would have *wrongly* promoted 026 and a sibling case (067) to `scam`, breaking two
already-passing tests, while two legitimate-but-narrow "likely_scam" benchmark cases that currently
depend on the waterfall picking an L-rule over a weak score (010, 064) would also have flipped the
wrong way.

The fix actually applied is narrower and evidence-based: an L-rule's `likely_scam` is escalated to
`scam` only when a **genuinely independent** signal is also present — one of the PRD's named critical
mechanisms (OTP/credential harvesting, wallet exploitation, extortion, a verified deceptive
destination), or the two new severe-manipulation/money-mule signals above — and, for the four
call-only KB patterns (bank/government/tech-support/delivery call), only the severe-manipulation/
money-mule signals apply, because those four patterns are correctly capped at `likely_scam` even on a
full match by PRD design (confirmed by `tests/test_call_investigation.py`, which was the regression
caught and fixed mid-pass).

## What's still only advisory, not a gap

`calibration_results.json`'s `scoreDelta` column shows several settled cases land a few points below
their illustrative target score (e.g. 002 at 75 vs. target 96) while still matching the target *tier*
exactly. Per the test suite's own design (`test_case_reaches_the_target_finding_tier`), only the tier
is a hard assertion — the exact score is "advisory only". A second diagnostic pass found 8 of these
(002, 006, 008, 010, 026, 064, 067, 084) where the reported tier and the raw 0–100 score still
disagree slightly, in both directions, with no regression introduced by this pass (confirmed by
comparing full before/after dumps of every case). Fully eliminating that residual gap would mean
re-tuning the six scoring dimensions' point values case-by-case, which risks exactly the kind of
threshold-weakening this pass was told to avoid — flagged here for a future, dedicated pass rather
than patched now.
